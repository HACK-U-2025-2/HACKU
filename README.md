# 開発ルール

## Github Project
- プロジェクト管理はgithub projectを用いて行う
- github projectでは複数テーブルがあり、sprintの若い順か開発を進めていく
- 各sprintは実装する機能の優先度を表しており、例えばsprint1はMVPに相当する機能を指す
- 各担当(front, server, AI)について、該当sprintの実装を完了した場合にのみマネージャに確認をとった上で次のsprintの開発に進むことができる
- テーブルには以下のカラムがある
  - TODO: タスク分解のみ行われ、実装者が決まっていない未着手のタスク
  - In Progress: 現在着手中のタスク
  - In Review: サブissueについて、実装済みでレビュー待ちのもの
  - In Manager Review: 親issueにおいて、サブissueの分解後にマネージャーレビュー待ちのもの
  - DONE: レビュー完了後で、マージ済のタスク
- TODOのタスクはマネージャが作成する

## 開発フロー
- TODOから担当するタスクを選び、アサイナーを自身に設定し、In Progressへ移動する
- 親issueについて、必要な機能単位でサブissue(最低1つ)を作成し、親issueをIn Maneger Reviewへ移動させる
  - サブissueのタイトルには必ず"sprint〇:"をつけること
- sprint〇ブランチからサブissue用のブランチを派生させ、作業する
  - ブランチの命名規則はないが、わかりやすいものがよい
  - 親issueに対しブランチを切り、作業することは今回禁止する
  - ブランチはサブissue単位で切ること
- 作業完了後、sprint〇ブランチに対しプルリクを作成し、close, relateでサブissue, 親issueの紐づけを明示する
  - コミットメッセージに対しても規則はない
- プルリクにレビュワー、アサイナーを設定し、Discordにてプルリクを出した旨を伝える
- タスクをIn Reviewへ移動させる
- 修正が必要な場合はIn Progressへ移動されているので対応後再びIn Reviewに戻す
- 全レビュワーの承認した後、マージされているのでタスクをDONEに移動して完了とする
- なお、コンフリクトが発生しないことが明らかな場合ではタスクを同時に受け持ってもよい
## レビュー
- レビュー時には特に以下を確認する
  - マージ先のブランチが適切か(重要)
  - プルリクの目的が達成されるか
  - 正常な動作が確認できるか
  - 無関係な変更が含まれていないか
  - 可読性が十分か
  - エラーハンドリングが適切か
- プルリクの最後の承認者はマージ作業をおこなうこと
  - 2人承認されないとマージできない設定
  - レビュワーが3人いる場合、3人目の承認なしにマージできてしまう点に注意
- 必ずコメントを残し、レビュー対応した旨をDiscordで報告すること
  - 修正が必要な場合はタスクをIn Progressへ移動させること
- 各メンバーの担当レビュワーは以下となる(敬称略)
  - 大澤: 松尾(Mattya3)、池田(Rozelin-dc)、森(marie1a22)(デザイン、動作を確認)
  - 池田: 松尾(Mattya3)、大澤(tyPhoon)、森(marie1a22)(デザイン、動作を検証)
  - 松尾: 大竹(ootake430)、大澤(tyPhoon)
  - 大竹: 松尾(Mattya3)、大澤(tyPhoon)
- マネージャーレビューでは、親issueを達成するためにサブissueで過不足ないかが確認される

## Discord
- 利用は自由。明文化はされているが、縛りではない
- 以下の内容についてチャットが使用される
  - プルリク作成の連絡
  - レビュー対応完了の報告
  - プロダクトに関する質問
    - 森さん(+必要に応じて松尾)にメンション
  - 実装方法・技術に関する質問
    - 同担当者または松尾にメンション
  - 進捗報告
    - 毎日簡単でいいので報告する
    - 困りごとものせていい
  - 雑談やその他
    - 大歓迎
- ボイスチャンネルは自由に使用してよい
  - 作業時とかここにいると質問しやすいかも

## マネージャー
- メイン作業はGithub Projectの管理
  - 特に、作業がない人がでないようTODOのタスクは作成しておくこと
- 週に1, 2回はミーティングを開き、全体で進捗・困りごとの確認をすること
  - プロジェクトの進捗、期間内に終わるかは特に注視しておく
- 最初の方はProjectの管理は松尾が行うが、後半は森さんメインで担当していく
